2. Camera input and Session processing
Snap's documented Android entry point is Session.

The Camera Kit Android documentation explicitly defines a Session as a rendering pipeline that connects a media input source to its AR engine, applies a Lens and produces rendered output.

Its actual public integration looks conceptually like this:
val imageSource = CameraXImageProcessorSource(
    context = context,
    lifecycleOwner = lifecycleOwner
)

val session = Session(context) {
    imageProcessorSource(imageSource)
    attachTo(cameraKitViewStub)
}


The important details:
- CameraXImageProcessorSource supplies camera frames.
- Session.Builder configures the processing pipeline.
- Session.processor manages image and other media-processing operations.
- Session manages the lifecycle of its components.
- Input sources are attached when the Session starts and detached when it closes.
- An output is connected to display the processed camera stream.
If no continuous image input is connected, Lens features that depend on frames cannot produce their output. 
Lens Studio Docs+3


This is the first actual architectural abstraction Snap exposes: a persistent processing Session rather than independent processing operations initiated by individual effects.
3. Lens Runtime — how the effect itself executes
This is the next important part.

Snap's public LensesComponent.Processor API describes a processor that extends the image, audio, user-data and other processing interfaces. Its documented responsibility includes applying and removing Lenses on the incoming media streams.

Its main operations include:
Operation	Responsibility
apply()	Apply the requested Lens
clear()	Remove the currently applied Lens
warmup()	Preload a Lens for faster activation
prefetcher	Fetch Lens content before activation
cache	Manage available Lens resources

Crucially, applying a Lens is an asynchronous operation. The SDK provides a callback indicating success or failure.

The warmup() API, introduced in Camera Kit 1.45, prepares a Lens by applying it to preload resources without rendering it. This operation is limited to first-frame resources; multiple warmups may affect the active Lens's performance. 
kit.snapchat.com+3


This gives us a clear distinction:

Lens activation, Lens asset loading and continuous frame execution are separate responsibilities.

A Lens is not simply a texture file loaded directly into a shader.
4. Face perception and tracking — the most important technical layer
Snap exposes multiple specialized face-related capabilities.
System	What it provides
Face Detection	Detects and acquires a face
Face Landmarks	2D facial reference points
Head Binding	Head position and orientation for attached objects
Face Mesh	Deforming 3D facial surface
Face Expressions	Facial expression information
Face Mask	2D texture projected onto a face
Face Occluder	Hides virtual objects behind facial geometry
Face Retouch	Facial enhancement effects

These are separate developer-facing capabilities exposed in Lens Studio, not evidence that every Lens runs every model. 
Lens Studio Docs+2


There is another useful feature called Tracking Scope.

Snap uses it to associate multiple tracking components with a common tracked person. Its documentation specifically describes cases where body and face trackers may otherwise disagree about which person is being tracked. 
Lens Studio Docs+1


This means its tracking architecture accounts for the relationship between tracking components, not just individual detection outputs.
5. What Snap's patents reveal about actual face stability
This is where the research becomes considerably more interesting.

Snap has a patent titled:

Region-based stabilized face tracking — US12299905B2, published May 13, 2025.

It describes a particular face-tracking method designed to achieve stable real-time tracking. This is much more informative than the basic Lens Studio interface documentation.

patents.google.com+1
A. It does not treat the whole face as one rigid object
Snap's patent explains that different facial regions behave differently.

For example:
- Forehead: comparatively rigid.
- Nose bridge: comparatively rigid.
- Cheeks: deformable.
- Mouth and jaw: highly expressive.
- Eyebrow regions: independently deformable.
The patent describes partitioning the face into spatially adjacent regions based on how groups of vertices move together.

It then uses region-specific models instead of relying entirely on one global linear face model. Its described model can contain 1,220 vertices, with shared vertices between neighbouring facial regions. 
Google Patents+1









pmc.ncbi.nlm.nih.gov


B. Each region has two kinds of motion
This is particularly important.

The patent describes two parameter groups for facial regions:

1. Rigid parameters

Six-degree-of-freedom motion, representing regional rigid movement.

2. Non-rigid parameters

Expression and deformation coefficients, representing local facial changes.

The system assigns dynamic rigidity weights to regions. Regions undergoing greater expression deformation can have less influence over the global rigid-pose estimation.

Why?

Because when a person opens their mouth or smiles, the algorithm should not interpret that local deformation as a large head movement.

This is one of the central ideas in the patent. 
Google Patents+2

C. It combines landmarks and dense optical flow
The patent explicitly points out a limitation of sparse landmarks: landmarks alone cannot recover all the motion in regions without sufficient tracked points, such as the cheeks.

It therefore describes:
1. Detect facial landmarks.
2. Calculate dense optical flow within the face region.
3. Map flow vectors onto projected face-mesh vertices.
4. Use the flow information alongside landmark constraints.
In effect, landmarks provide sparse geometric evidence, while optical flow supplies denser motion evidence. 
Google Patents+1

D. It alternates pose optimization and expression optimization
This is arguably the most important part of the disclosed tracking algorithm.
Tracking optimization loop
Step 1 — Rigid Pose Optimization

Hold expression parameters fixed.

Estimate head pose using:
- Facial landmark constraints
- Dense optical-flow constraints
- Previous-frame temporal coherence
- Region-specific rigidity weights


Step 2 — Expression Optimization

Hold rigid pose fixed.

Estimate regional facial deformation using:
- Landmarks
- Optical flow
- Temporal coherence
- Sparse expression coefficients
- Boundary consistency between regions

Alternating optimization of pose and expression
Step 3 — Stabilized Face Model

Combine regional results, reconcile shared vertices and produce the tracked 3D facial surface.


The patent explicitly describes these alternating optimizations and the use of temporal coherence to regularize results against previous estimates. 
Google Patents+1


Notice the difference: this is not simply applying a smoothing filter independently to each landmark. It is jointly considering facial structure, rigidity, deformation, motion evidence and previous state.

This is one of Snap's most useful public technical disclosures for understanding face-tracking stability.
6. Another important pipeline: asynchronous processing
Snap has another patent:

Real-time tracking-compensated image effects — US11989938B2, published May 21, 2024.

It describes an architecture for expensive image-processing effects, particularly CNN-based image segmentation and masks.

The system uses two asynchronous pipelines.
Pipeline A — Expensive processing
Frame K1 → CNN → Modified output M1
Frame K3 → CNN → Modified output M3
The expensive image-processing model may process only selected frames and lag behind live input.
Pipeline B — Fast tracking compensation
Current frame + last processed frame

Optical-flow map

Warp previous CNN output to current frame

Combine outputs → Real-time display


For example, imagine the expensive CNN is five frames behind the camera.

Instead of waiting for it to process every missing frame, the faster tracking pipeline calculates optical flow from the last CNN-processed frame to the current frame. It applies that flow map to the previous modified image or mask.

The result is a current-frame approximation while the expensive pipeline continues working.

The patent explicitly describes separate asynchronous pipelines, potentially running on separate threads. 
Google Patents+3


Important qualification: this is a patented technique for computationally intensive image effects. It does not prove that all face-tracking or all LensCore effects use this exact mechanism.
7. Scene execution — how the Lens operates every frame
Lens Studio's scripting documentation exposes a defined event lifecycle.
Event	Documented execution
OnAwake	Component construction or deserialization
OnStart	First enabled frame, before rendering
Update	Per-frame component update
LateUpdate	After Update, animation, physics and tracking; before rendering
OnDestroy	When component is destroyed
OnEnable / OnDisable	Component activation/deactivation


Lens Studio Docs+2
The particularly interesting part is LateUpdate.

Snap documents that it runs after tracking systems and before rendering. That allows scene components to consume updated tracking state before their frame is drawn.

This tells us something important about Lens execution: the script lifecycle and tracking lifecycle are coordinated with the rendering lifecycle.
8. The rendering pipeline
Lens Studio's Camera component renders selected SceneObjects into Render Targets.

Each camera has configurable:
- Render layers.
- Camera type: Perspective or Orthographic.
- Render order.
- Input texture.
- Depth mode.
- Clear depth.
- Mask texture.
- Render Target.
Multiple cameras can share one Render Target, and render targets can feed subsequent camera passes. Snap recommends keeping unnecessary cameras and render targets to a minimum. 
Lens Studio Docs+1


A useful example is the post-processing system.

Screen Texture provides access to the current Render Target contents. A later shader can therefore consume the image as modified by preceding draw calls. 
Lens Studio Docs


Depth is also part of the rendering architecture:
- The Face Occluder is a 3D facial model that hides parts of attached virtual geometry.
- Occluder materials can mask virtual objects.
- Body Depth Texture can supply per-pixel person-depth information for virtual object occlusion.

Lens Studio Docs+2
Finally, Snap's Scene asset distinguishes:
- Live Target: the output shown during live camera use and recording.
- Capture Target: the output used for the final captured Snap.
- Overlay Target: a separate native-resolution target for UI-like content.
The live and capture targets may be different or shared depending on the Lens. 
Lens Studio Docs+1

10. The final reconstruction
Putting the public material together, the most defensible description of Snap's architecture is:
1. Session layer: owns the continuous media-processing lifecycle.
2. Lens processor: receives input streams and executes the active Lens.
3. Perception layer: provides shared face, head, expression, body and other tracking capabilities to scene components.
4. Temporal tracking layer: maintains consistent tracking state. Published face-tracking patents describe regional rigidity, pose/expression separation, optical flow and temporal regularization.
5. Scene runtime: executes components, scripts, animations and transforms within a defined lifecycle.
6. Render graph: executes ordered camera passes, materials, depth operations, post-processing and render-target composition.
7. Output layer: produces live preview and capture output.
8. Resource lifecycle: loads, caches, prefetches and releases Lens assets and runtime resources.
One critical thing to remember: Snap's stability is not attributable to one face-tracking model. Its documented architecture and patented methods reveal multiple cooperating systems, operating at different points in the frame lifecycle.
